# 设计哲学

## 一句话

**数据定义是圆心，所有代码围着数据转。先定形状，再写实现。**

---

## 一、数据驱动开发

传统 MVC 教法是：需求 → 建表 → Model → Controller → View。但表是给数据库看的，不是给需求看的，两轮翻译下来代码和 PRD 经常对不上。

这个项目的做法是把数据定义提到最前面：

```
需求 → schema/do/ → schema/vo/ → domain/ → db/ → services/ → api/
       └─ 形状 ─┘                         └─ 实现 ─┘
```

### DO（Data Object）—— 数据库的 Python 投影

DO 不是"和表长得像的类"，它就是表在代码里的表达。每一个字段都对应数据库里的一列，不多不少。DO 写完，`CREATE TABLE` 的 SQL 就自动推导出来了——字段名、类型、是否可空，全部对齐。

### VO（View Object）—— 前端的活合同

VO 决定了前端看到什么、字段叫什么、类型是什么。`to_vo()` 转换函数里写着所有格式化逻辑——时间怎么转字符串、数字怎么变描述、关联字段怎么 JOIN。打开 `schema/vo/`，前后端对接不需要文档。

### 为什么这样做

- **需求变了，先改 DO/VO**：改动范围可控，不用追到 services 里 debug
- **代码即文档**：新人打开 `schema/` 看一眼就知道数据库结构和前端接口
- **字段改名的成本极低**：IDE 的"重命名符号"顺着类型标注一路改到底，不会漏

## 二、六层架构：每一层为什么存在

```
Connection → DO → DAO → Service → Domain ← API
```

### Connection（连接池）
**为什么有**：每次请求新建 TCP 连接是 20-30ms，从池里拿是 0ms。这一层的存在纯粹因为"快"。

### DO（数据对象）
**为什么有**：dict 没有类型检查。`row['title']` 拼错成 `row['titel']` 运行时才发现。DO 让 IDE 在写代码时就报错。

### DAO / DB（数据访问层）
**为什么有**：把 SQL 关在一层里。如果换数据库（MySQL → PostgreSQL），只改这一层。如果 SQL 散落在 services 里，换数据库等于重写项目。

### Service（业务逻辑层）
**为什么有**：权限校验、通知触发、内容截断、数据转换——这些是"业务规则"，不是"数据存取"。放在 DB 层会让 DB 层承担判断职责；放在 API 层会让 HTTP 和业务耦合。Service 是唯一能写 if-else 的地方。

### Domain（接口层）
**为什么有**：API 不依赖具体 Service，只依赖接口。换实现只改工厂函数；写测试时 mock 接口替换真实服务。这是依赖倒置——高层和低层都依赖抽象。

### API（路由层）
**为什么有**：HTTP 的事归 HTTP——解析 Query 参数、校验 token、返回状态码。这一层不写业务逻辑，只做参数转发。

### 核心规则

```
数据从内往外流：Connection → DO → DAO → Service → Domain → API → HTTP
依赖从外往内指：API → Domain ← Service → DAO → Connection
```

**依赖箭头永远指向内层，数据箭头永远流向外层。** 这是六层的全部规则，记住这一句就够了。

## 三、加新功能的标准流程

以加一个"资源下载"功能为例：

| 步骤 | 做什么 | 产出 |
|------|--------|------|
| 1. 定形状 | `schema/do/resource.py` 写 ResourceDO | 数据库结构确定 |
| 2. 建表 | 从 DO 推导 CREATE TABLE SQL | 数据库就绪 |
| 3. 定输出 | `schema/vo/resource.py` 写 ResourceVO + to_vo() | 前端合同确定 |
| 4. 签合同 | `domain/resource.py` 写 IResourceService(ABC) | 功能清单确定 |
| 5. 写查询 | `db/resource_db.py` 写 SQL → DO | 数据通路打通 |
| 6. 写逻辑 | `services/resource.py` 实现接口 | 业务逻辑完成 |
| 7. 挂路由 | `api/v1/resource.py` 写端点 | HTTP 入口就绪 |
| 8. 注册工厂 | `core/deps.py` 加 get_resource_service() | 依赖注入就绪 |

前四步不写一行实现代码，但模块的全貌已经清楚了。后四步只是逐层"填空"。

## 四、温度体系的设计思想

情感分析模型搭载了六层温度缩放后处理。它不是"调参数调出来的"，而是从错误中长出来的——每一层都对应一个被发现的盲区。

| 层级 | 解决的问题 | 核心思想 |
|------|-----------|----------|
| L1 短文本兜底 | 单字"好""差"在 50 位 padding 中信号消失 | 规则覆盖网络的盲区 |
| L2 注意力熵检测 | 区分"模糊评价"和"清晰评价" | 不确定时承认不确定 |
| L3 置信度门控 | 模型确定时不误压，不确定时不硬撑 | 分级信任，不一刀切 |
| L4 中性词保护 | "勉强还行"被判 83% 正面 | 语义优先于统计 |
| L5 转折词触发 | "讲课好，但节奏快"被判 92% 正面 | BiGRU 的结构局限 |
| L6 极端词降温 | "太棒了"被压到 55% | 强信号不需要修饰 |

### 三个核心原则

**1. 尽量相信模型，除非有理由不信。** 温度体系的默认状态是低温低混——让模型正常输出。只有检测到异常信号（中性词、转折词、高熵、不确定）时才干预。

**2. 温度翻不了方向。** 温度只能把 90% 压到 65%，不能把正面翻成负面。模型原始判断错了，后处理救不回来。真正的天花板是标注数据的质量和数量。

**3. 承认局限，用规则守住底线。** BiGRU 对 A-but-B 句型有先天偏向——这不是 bug，是架构层面的取舍。30+ 转折词规则是实用主义妥协，最优解是更大的标注数据。这是一种工程上的诚实：知道工具的边界在哪里，在该兜底的地方不犹豫。

## 五、设计 Token 体系

前端视觉收敛到一套 Design Token（CSS 变量）：品牌色、语义色、文字色、间距、圆角、阴影、动效时长，全部抽成变量。加新页面时只引变量不写死值，自动保持视觉统一。暗色模式通过 `[data-theme="dark"]` 一套选择器全局切换，不维护两套样式代码。

原则：**一致性不是靠"照着写"保证的，是靠"只能这样写"保证的。**

## 六、工程价值观

### 架构的每一层都要能回答"为什么存在"

不能因为"Spring Boot 就是这么分的"或者"网上教程这么写的"。每一层要么解决一个具体问题，要么就不存在。

### 数据是天花板

再精巧的后处理也补不齐糟糕的数据。六层温度体系不如再标注 500 条 A-but-B 评语。工具的上限是数据的质量。

### 代码是写给人的

注释解释的是"为什么这样做"而不是"做了什么"。`predictor.py` 里 200 行注释，每一段都在回答一个问号。不是为了凑字数，是因为六个月后的自己也需要重新理解这些决策。

### 一个人的全栈不是妥协

没有后端团队、没有前端同事——这反而逼出了更清晰的架构。因为如果自己不把边界划清楚，三个月后改代码的人（还是自己）会在 if-else 里迷路。
